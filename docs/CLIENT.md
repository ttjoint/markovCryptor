# 新客户端（client）——最终形态与决策

> 状态：**决策已定，进入实施**。本文只写「为什么这样做」和「做出来是什么」；
> 逐步施工顺序见 `CLIENT_PLAN.md`。
>
> 已有的测试端（`markovcryptor/web_terminal.py` + `markovcryptor/webui/`）**保留不动**，
> 它是唯一在真机上验证过的形态，真出问题时的对照组。

## 1. 一句话

把现在这个「本机两个窗口的点到点演示」改造成**挂在 QQ 上的实际通信终端**：
一台设备一个 QQ 号，界面上是好友列表，每个好友一条独立信道，普通消息照常
收发，藏了密文的消息在单独窗口里显示。

## 2. 与测试端的区别

| | 测试端 | client |
| --- | --- | --- |
| 终端数量 | 固定 alice/bob 两个 | **每个好友一条**，按需创建 |
| 对端寻址 | `--peer` 手填 QQ 号 | 从好友列表点选 |
| 消息 | 只有混淆消息 | 普通 QQ 消息 + 混淆消息 |
| 启动 | `chat.bat -Peer xxx` | 双击 exe，全程 GUI |
| 数据留存 | 内存 | **内存**（明确不落盘，见 §5） |
| 平台 | Windows + 手装 py/node | Windows 10/11，**零安装** |

## 3. 部署形态

**每台设备 1 个 QQ + 1 个本系统实例。** 不是同机双号。

同机挂了多个 QQ 的少数情况：启动时在 GUI 里列出来让用户选，**不要求用户
在控制台敲任何参数**。

## 4. 界面

```
┌─────────────┬──────────────────────────────────────────┐
│ 好友列表     │  与 某好友  的对话                        │
│             │  ┌──────────────┬──────────────────────┐  │
│ ● 三马赫 ②  │  │ 明文窗口      │ 密文窗口              │  │
│   术力口    │  │              │                      │  │
│ ● 某人      │  │              │  [发起密钥交换]        │  │
│             │  │              │  待发图片 3 张         │  │
│             │  └──────────────┴──────────────────────┘  │
└─────────────┴──────────────────────────────────────────┘
```

- **左侧**：好友列表，从 QQ 拉取。未读红点、信道状态标记。
- **右侧**：沿用 alice 那套——左明文窗、右密文窗、图片队列。
- 点开某个好友**才**拉它的历史消息（不预取全部 29 个）。

## 5. 数据不留存（硬性要求）

**本系统不落盘任何用户数据。** 程序退出即销毁：

- 好友列表 — 每次启动从 QQ 读
- 聊天历史 — 每次点开好友时从 QQ 读
- 待发图片队列 — 只在内存
- 会话密钥 — 只在内存（本来就不该落盘）

这不是"省事"，是产品定位：我们卖的是隐私混淆通信，如果自己囤一份 QQ 聊天
记录副本，就自相矛盾了。

副作用要在 UI 上说清：**图片队列关闭即清空**。用户会以为这是 bug，必须
在界面上明写，不要让他们猜。

## 6. 图片队列

用户登记一个或几个**图片文件夹路径**（配置文件，只记路径和选项，不复制图）。

- 进队时从文件夹里挑一张还没用过的，加进队列。
- **预筛**：进队时就判断这张图装不装得下握手报文，装不下直接跳过并记一行日志。
  等发的时候才发现装不下，用户已经排队等了没意义。
- 队列上限 **5~10 张**（可配），避免用户有个几千张表情包的文件夹把程序拖死。
- 取图模式可配：**随机** 或 **按名称顺序**。
- **不删用户的图**，只是出队。下次启动可能重复用到同一张 —— 用户自己管。
  这条要写进配置注释，否则"为什么又发这张"会被当成 bug。
- 队列**不落盘**，见 §5。

## 7. QQ 消息的解析范围

QQ 的消息类型极其庞杂：自带表情、多媒体、XML/JSON 卡片、嵌套转发、语音、
窗口抖动…… **不全解析。**

只重点解析信道用得上的两样：**图片** 和 **文本**。

其余一律在对话列表里显示一行小字，例如「对方发送了 语音」「对方发送了 窗口抖动」
「对方发送了 一条转发消息」。不解析、不展开、点了也不做任何事。

顺手能解析的可以做，但**展示方式要与 QQ 一致**，否则用户会觉得怪异。

> 实现前可参考 GitHub 上那些自己接 OneBot 接口做的美化版 QQ 客户端，
> 抄它们的消息分类思路。

### 7.1 信道隐身的铁律

**文本解不出来时，不回任何东西。宁可对面收不到回应。**

这条比"好用"优先级高。理由：任何自动回包都可能在信道上留下可被识别的
程序化痕迹。我们要求这个信道看起来就是两个正常人在聊天。

推论：
- 解密失败 → 静默丢弃，不回复、不提示对端。
- 没有共同文本模型 → 静默，不告知对端 fingerprint。（用户自己从本机日志看）
- **非必要不通过信道发任何东西。**

## 8. 文本混淆与模型协商

### 8.1 不需要改协议

实测 `markovcryptor/codec.py:278` 的 `identify_model()`：模型指纹被写进帧的
校验码，**解码端持有一批模型时能从开头十几个汉字认出是哪个模型**。

所以"双方有哪些模型"不用协商 —— 各加载各的，能认出来就解，认不出来就静默。

| 方案 | 握手帧增量 | 判定 |
| --- | --- | --- |
| 握手帧塞模型清单 | +32 字节/模型 | **否决**：要改帧格式，破坏兼容 |
| 自动识别 + 失败静默 | **0 字节** | **采用** |

### 8.2 加载代价

实测单模型 **0.53 秒 / 17.6MB**。4 个模型 = 2.1 秒 / 70MB。

**不能启动时全加载。** 用懒加载 + 指纹索引。

### 8.3 用户自训练 / 导入导出

现有能力已具备（`MarkovModel.train()`、`markovcryptor train` 命令、
`markovcryptor identify`）。客户端只需把它 GUI 化：

- 选语料文件 → 训练 → 存进用户模型目录
- 导入：把 `.json` 拖进目录
- 导出：从目录复制走

**排在后面做**，当前主战场是图片信道。

## 9. UI 技术选型

**本地 HTTP 服务 + 用系统默认浏览器以 `--app` 模式打开。**

- 探测系统默认浏览器（用户可能设成 Chrome / Edge / Firefox）。
- Chrome / Edge 都能用 `--app=URL` 打开一个**没有地址栏和标签页**的独立窗口，
  视觉上就是个原生应用。
- Firefox 没有等价的 `--app`，降级为普通标签页 + 提示。

为什么不用别的：

| 方案 | 否决理由 |
| --- | --- |
| Tkinter | 红点/缩略图/虚拟滚动/圆角全要自绘，几千条消息性能差，做不出 QQNT 的观感 |
| Electron | 塞一整个 Chrome，+150MB，为了个聊天界面不值 |
| Tauri | 要 Rust 工具链，且 Win10 不保证有 WebView2 Runtime |

浏览器方案 **0 额外体积、0 额外依赖**，调试就是普通网页。

## 10. 启动（零安装）

用户机器上**没有 Python、没有 Node** 也要能跑。

```
用户双击 launcher.exe
  ↓ .NET Framework 4.8（Win10 1809+ 内置，实测 4.8.10008 自带 csc.exe）
检查包完整性
  ↓
起包内 Python（embeddable，绝对路径）
  ↓
起包内 Node + SnowLuma
  ↓
轮询 get_login_info，直到 QQ 登录（提示"请登录 QQ"）
  ↓
起本地服务 → 默认浏览器 --app 打开
```

### 10.1 为什么自带 Python 而不是让用户装

- Python embeddable 的 `Lib` 去掉 `site-packages` 只有 **21.8MB**
- 加上 numpy / pillow / cryptography / fastapi 等 wheels 约 60~70MB
- 比"让用户装 Python 3.11+ 和 Node 18+"的体验好一个数量级

### 10.2 一个必须避开的坑

`C:\Users\<用户>\AppData\Local\Microsoft\WindowsApps\python.exe` 是微软商店的
**stub**（实测指向 `AppInstallerPythonRedirector.exe`），直接调 `python` 会
弹商店或失败。

**启动器必须用包内 python.exe 的绝对路径**，不能裸调 `python`。

## 11. Android：当前不可行，明确搁置

实测 `snowluma/native/`：

```
snowluma-win32-x64.dll
snowluma-win32-x64.node     ← 注入 Windows 版 NTQQ 进程
websocket-win32-x64.node
```

SnowLuma 是**直接注入 Windows 版 QQ 进程内存**的。手机 QQ 是完全不同的
协议栈（原生 ARM，非 Electron），**没有可注入的等价点**。

要走 Android，唯一路径是自己实现 QQ 协议（登录、心跳、加密、收发、风控对抗），
那是本项目的几倍工作量，且封号风险极高。

**结论**：Android 用户只装普通 QQ，不装我们的端。将来若一定要手机端，
更现实的做法是 Windows 上的端开一个局域网可达的服务，手机浏览器访问。

## 13. 传输层三个必须先修的问题

**这是地基，UI 再漂亮也压不住它的塌方。**

1. **入站是全广播的。** `onebot.py:518` 把每条消息发给所有 sink，不按发送者
   过滤。现在只有一个终端所以看不出来；一接多好友，A 的消息会串进 B 的会话。
2. **没有请求-响应。** 只有 `send`，没有 `ask`。好友列表、历史消息、登录信息
   全要用到 `echo` 匹配的请求响应。（三个接口已实测可用：`get_friend_list`
   返回 29 个好友、`get_friend_msg_history`、`get_stranger_info`。）
3. **没有原始事件回调。** 普通 QQ 消息目前被隐写层直接丢弃，界面上要看
   「对方发送了图片」就必须把它透传上来。

## 14. 术语

- **信道**：与某个好友之间的混淆通信通道。建立后才有密文窗口的内容。
- **握手帧**：一张图，里面藏着 X25519 公钥。
- **底图 / 封面**：没藏东西的真实照片，用来触发握手或作为密文载体。
- **测试端**：`markovcryptor/web_terminal.py` 那套 alice/bob 双窗口演示。
