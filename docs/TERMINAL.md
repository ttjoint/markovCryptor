# 点到点通信终端（PBX1）设计

> 状态：**可行性验证已完成**。本文固定协议与判定规则；
> 实现见 `markovcryptor/terminal/`，测试见 `tests/test_terminal*.py`。

## 1. 目标与边界

做一个**像聊天软件的双人终端**：用 ID 收发消息，对端看到消息后**自动判断**
其中有没有隐写，然后把结果分发到两个窗口——

- **聊天窗口**：正常内容。没隐写就是文本/图片本身；有隐写时**宿主照常显示**。
- **隐密窗口**：从隐写里恢复出来的内容。正常消息时它**一动不动**。

这个「自动判断」是整个设计里最关键的地方，因为它必须**永远不能把正常消息
误判成隐写**，否则用户会看到一条凭空出现的密语；反过来把隐写漏判成正常消息
则只是功能缺失，不会误导。所以判定规则被设计成**只能靠"密码学上成立"来确认**：
AES-GCM 认证标签对不上，就一律当作没有隐写。

### 不做什么

- **不做中心服务器。** 终端之间点对点，`id` 只是本机寻址用的名字。
- **不做可靠传输。** 底层是内存/文件队列（测试替身），不实现重传。
  真实网络传输是可替换的传输层，本期只保证协议层正确。
- **不做群聊、历史同步、离线消息。** 都不是验证可行性需要的东西。

## 2. 消息模型

一条消息 = **文本（0~m 字节）+ 图片序列（0~n 张）**，作为**一个数据包**发送。

```
Packet {
  text:  str | None          # 明文文本
  images: [bytes, ...]       # 原始字节（PNG/JPEG/GIF 原样）
}
```

接收方对**每个**字段独立判断是否隐写。这条规则很重要：同一包里
「文本有隐写、图片没有」是合法状态，两个窗口要分别显示。

## 3. 隐写信封（PBX1）

隐写载荷不是裸数据，而是一个信封，放在 MKX1 帧**内部**：

```
MKX1 帧 (core/framing.py, 冻结)          ← 引导头/CRC/RS/白化
└── payload (本协议)
    ├── MAGIC "PBX1"      4 B
    ├── type              1 B     H=握手  B=正文  T=纯文本正文
    ├── body              rest
    └── 校验由 MKX1 的 CRC16 + RS 负责，另加 GCM 认证标签
```

三种类型：

| type | 含义 | body |
|---|---|---|
| `H` 握手 | 通报本端 X25519 公钥，或回应对方 | `pub(32) \| mode(1)` |
| `B` 正文 | 加密后的正文，某张图片里 | `nonce(12) \| AES-GCM(key, plaintext)` |
| `T` 纯文本正文 | 加密后的正文，藏在**文本**里 | 同上 |

**为什么正文要分 `B` 与 `T`：** 两者加密密钥相同，但载体不同。分开类型
让接收方不必先去猜"这条是从图里还是从文本里来的"，也让日志能直接说出
是哪条信道承载的——排查问题时这非常有价值。

**为什么要 `mode`：** 握手报文必须区分「首次请求（我要跟你建会话）」和
「回应（我收到了，这是我的公钥）」。没有它，双方会各发一个请求、
互相都在等对方的回应，永远建不起来。

## 4. 密钥交换（只在图片里发生）

沿用 `handshake.py` 的 X25519 + HKDF，但补上**状态机**——原实现只做了
密码学，没约束"什么顺序才算建好"，而终端恰恰需要这个。

```
        ┌──────────┐  对端 H(request)   ┌────────────┐
        │  IDLE    │───────────────────→│ RESPONDING │
        │ (无会话) │                    │ (已回发)   │
        └──────────┘                    └────────────┘
              ↑                              │
              │ 收到 H(response)             │ 收到 H(response)
              └──────────────────────────────┘
                        ↓
                   ┌─────────┐
                   │ ESTAB   │  可收发密文
                   └─────────┘
```

- **只有图片能承载握手。** 文本信道（中文信道）容量太小且需要模型，
  不作为握手载体。这一条直接来自需求，也符合物理：握手报文共 38 字节
  （4 字节信封头 + 32 字节公钥 + 1 字节模式 + 1 字节类型），
  一张 120×120 的图（74 字节）就装得下，160×160 则很宽裕。
- **收到 `H(request)` 必须自动回一张带 `H(response)` 的图。** 这是需求的
  核心：一次点击之后不需要人工干预。
- **`H(response)` 到达即进入 ESTAB。** 因为 X25519 是单向通报，双方
  各自都能独立算出同一个共享密钥。

### 重放与降级

- 每次握手用**新的临时密钥对**，因此重放旧握手图不会命中已有会话——
  它会派生出一个对方并不知道的密钥，后续正文全部认证失败、被忽略。
  这比"检测重放"更简单也更安全。
- **建立了会话之后，不再回到 IDLE。** 没有"降级到明文"的路径，
  除非对端显式发起新握手（那会产生一套新密钥，旧的作废）。

## 5. 判定规则：如何"尝试解密"

对收到的每个字段，按**固定顺序**尝试，全部失败即视为无隐写：

### 图片

```
1. 盲提取 (image_stego.try_extract)   → NoHiddenFrame? 视为无隐写
2. 帧里是 PBX1 信封吗？                → 不是，视为无隐写
3. 按 type 分派:
   H  → 交给握手状态机
   B  → 有会话? 无 → 忽略(记录 reason)；有 → GCM 解密
   T  → 图片里出现纯文本正文，忽略(类型与载体不符)
4. GCM 认证失败 (BadKey) → 忽略，记录"无法解密"
```

### 文本

```
1. 文本能被中文信道解码吗？  → 无模型/解码失败，视为无隐写
2. 帧里是 PBX1 且 type == T 吗？ → 否则视为无隐写
3. 有会话? 无 → 忽略；有 → GCM 解密
```

**关键：任何一步失败都不抛到用户面前。** 宿主内容照常显示，隐密窗口不动，
失败原因进日志。这是"非法隐写就忽略"的实现方式。

### 为什么不能只靠"解出来像不像文字"

因为那会把正常消息误判成隐写。GCM 认证标签是**唯一**能证明"这条消息
确实是知道密钥的人写的"的东西——它同时排除了随机噪声、损坏的载体和
别人的密文。没有认证的隐写检测只能靠启发式，而启发式在这件事上
错一次的代价（用户看到一条假密语）比漏一次的代价高得多。

## 6. 发送规则

界面只有一个文本框 + 一个图片序列 + 一个「密文」勾选框：

| 状态 | 允许 |
|---|---|
| 未建立会话 | **只能**明文发送（勾选框禁用） |
| 已建立会话 | 明文或密文皆可 |

- **明文发送**：文本 + 图片原样合并成一个包发出去。
- **密文发送文本**：隐密窗口的输入框 → 加密 → 藏进**文本**（`T`）→ 发出。
- **密文发送图片**：取**明文侧**的图片序列 → 把密文藏进图片（`B`）→
  连图片一起发出。文本侧明文照常附带。

### 为什么密文要单独一个输入框

需求明确要求"明文的文本和图片输入栏不变"。技术上也是对的：明文框的内容
要**原样**发出去（用户能看见它），而密文框的内容**永不显示**在对端聊天窗口里——
两者的可见性完全不同，混在一个框里会让"我这条到底会被谁看到"变得不可预测。

### 握手必须先选好图片

握手报文要藏进图片，所以点击「密钥交换」时图片序列里必须至少有一张能
容下 38 字节握手报文的图。装不下就直接报错并**逐张说明为什么**，不静默失败。
按实测容量：120×120 有 74 字节（刚好），160×160 有 162 字节（宽裕），
96×96 只有 34 字节（不够）。

## 7. 可行性验证环境

验证“这套协议真的能跑通”需要三个东西：

1. **队列传输**（`LoopbackNetwork`）：把包投递给指定 id 的终端。
   同步、确定、无需端口，测试可重复。投递由 `pump()` 显式驱动，
   不靠后台线程——所以“哪一步先发生”完全可控。
2. **两个终端**：各自有 id、密钥、状态机，接同一张网络。
3. **场景脚本**：握手 → 明文 → 密文 → 非法输入，断言两个窗口各出现
   什么、不出现什么。

`tools/terminal_demo.py` 提供一个可在终端里实际交互的版本，
用来人工确认“手感”对不对，而不是只信单元测试：

```bash
python -m tools.terminal_demo --steps   # 跑一遍固定场景，看两个窗口
python -m tools.terminal_demo           # 交互式，输入 send / hs / covert / fake
```

## 8. 实现过程中确认的两件事

这两条是写代码时才暴露出来的，写进文档是因为它们**不是代码细节，
而是协议行为**：

### 8.1 回应方在「回发」时就应该建好会话

最初的想法是：A 发请求 → B 回发 → A 收到回应才算建好，B 再等 A 确认。
这会**死锁**：X25519 是对称的，A 收到回应时也算出了同一个密钥，
没有任何东西要再发给 B。所以 B 在 `answer()` 里直接派生密钥。

### 8.2 “没有隐写”与“隐写被破坏”必须区分

`image_stego.try_extract` 原先把所有失败都包成裸 `StegoError`，
调用方无法分辨这两种情况。两者对终端的含义完全不同：

- **没有隐写**（正常照片）→ 属常规情况，只入调试日志，不给用户提示；
- **隐写帧损坏** → 值得告诉用户一句。

修正后 `try_extract` 保留原始错误类：一步都没找到帧 → `NoHiddenFrame`；
找到过但坏了 → `CarrierDamaged`。同理，底图太小原本抛裸 `StegoError`，
现在抛 `CapacityExceeded`（带 `reasons` 与 `hints`），
终端的“哪几张图装不下、分别为什么”才能逐张报出来。

> 注意：在 ECC 层，“口令错”与“载体损坏”天然不可分辨
> （`decode_lead` 的注释已说明）。因此即使分类正确，`CarrierDamaged`
> 仍可能来自一张从未隐写过的照片。终端因此用中性措辞“未读到隐写帧”，
> 而不是“隐写帧损坏”。

## 9. 已知限制

- **文本隐写需要模型。** `send_covert_text` 要中文信道的 `embed_text`，
  终端默认没有，调用会报 `InvalidInput` 并给出可操作建议。
  这是有意的：不让一个聊天模块隐式依赖用户数据目录。
- **握手回应图是自己合成的**（256×256 纹理噪声）。不是从对端拿到的
  图，所以看起来像噪声。能工作，但不够隐蔽——真实部署应当让用户
  预置一组底图，回应时随机选一张。
- **不防重放之外的重放。** 每次握手用新临时密钥，重放的旧握手图会
  导致后续正文全部认证失败（安全），但终端不会把这个事实告诉用户。
- **包内图片数量不设上限。** 传输层是内存队列，超大批次没有限制；
  接真实传输时需要加上限。
