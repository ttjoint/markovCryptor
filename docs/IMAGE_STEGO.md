# 图片频域隐写（MKX1）

`markovcryptor/image_stego.py` 在一个**普通图片**里藏入一段任意字节，接收方**不需要原图**（盲提取）
就能还原。它和中文信道（`codec.py`）是两条并列的可选信道，共用同一套“先封装帧、再上信道”的结构。

---

## 1. 为什么需要第二条信道

中文信道把比特藏进**汉字序列**，伪装对象是一段文本。它的缺点是：

- 只能通过文字载体传播（聊天、邮件、文档）。
- 中文信道的容量单位是“字”，而一个字约承担 `log2(3000) ≈ 11.55 bit`，一段 X25519 公钥就需要 23 个字。
- 大量实际传播场景只有图片（社交软件、图床、相册）。

图片信道把比特藏进**图像的 DCT 中频系数**，伪装对象是一张看起来完全正常的照片。
两条信道可以互相独立使用，也可以串联（先用中文信道得到文本，再把文本存进图片）。

---

## 2. 整体流程

```
payload (任意字节)
   │
   ├─ 引导头 lead (24 B)  ──  magic | ver | nonce | nblocks | length | CRC16
   │                          ↓ RS(40,24) 固定 1 块
   └─ 载荷 body           ── 按 207 B 分块
                              ↓ RS(<chunk>+16, <chunk>)  n 块
   │
   ▼
比特流 ── 每 8×8 块 4 bit ── 密钥决定的块顺序 ── 中心格点 QIM
   │
   ▼
YCbCr 某一通道（Y / Cb / Cr 自动择优）写回 ── PNG（无损）── 发送
```

接收方反向执行，**无需原图**：块坐标与通道都由共享密钥派生，帧头自带长度与块数。

---

## 3. 关键设计

### 3.1 载体：Y 亮度通道的 DCT 中频

图片切成互不重叠的 8×8 块，每块做二维 DCT。每块在固定的中频格点上取 4 个系数作为 4 条“车道”：

```python
LANE_VALUE = ((2,2), (2,3), (3,2), (3,3))   # (u, v)
```

选 `(2,2)…(3,3)` 是因为：低频改动会被人眼看出块状伪影，高频会被压缩算法直接丢掉，
中频处在“看不清”和“留得住”的平衡点。

### 3.2 QIM：中心格点量化

普通量化索引调制（QIM）把系数吸附到格点 `k * step`，判决边界就在格点上，
±1 的色域取整噪声就能翻转判决。本项目改用**中心格点**：

```
写入：coefficients[u,v] = (k + 0.5) * step      # k 的奇偶 = 该 bit
读取：shifted = c / step - 0.5
      k = round(shifted)
      bit = k & 1           # 奇→1，偶→0
      confidence = 1 - 2*|shifted - k|    # 0 在中心，1 在边界
```

写入点位于格**中心**，两侧各留半格余量，因此 ±半个 `step` 以内的扰动都不会翻转判决。
实测 RGB↔YCbCr 往返的 ±1 取整误差完全被吸收。

`step` 默认 10.0；底图平淡或颜色极端时自动降到 8 或升到 14（见 3.5）。

### 3.3 盲提取：块顺序由密钥派生

不需要原图，也不需要额外的坐标表：

```python
order = SHAKE256(key, "blocks", width, height, step) → numpy 随机置换
```

发送方按 `order[0], order[1], …` 依次使用块，接收方用同样参数得到同样顺序。
块总数是 `(width//8) * (height//8)`，所以**乱序使用整张图**，改动均匀分布在全图，
不会集中在某一条带（否则会被肉眼或直方图看出来）。

### 3.4 帧结构：双规格引导头 + 变长载荷

引导头是**唯一每个底图都要固定付出的成本**，而且它按块计价（不是按比例）。
一个 88 块的引导头占 120×120 小图的 39%，却只占 4096×4096 大图的 0.03%。
所以引导头有两档规格，由底图容量自动选择：

| 档位 | index | nonce | 明文 lead | RS 校验 | 码字 | 占块 |
|---|---|---|---|---|---|---|
| `LEAD_STANDARD`（宽松） | 1 | 8 B | 24 B | 20 B | 44 B | 88 |
| `LEAD_COMPACT`（紧凑） | 2 | 4 B | 16 B | 6 B | 22 B | 44 |

```
lead(standard) = MAGIC(4) | profile(1) | nonce(8) | nblocks(2) | length(2) | CRC16(2) | 填充(5) = 24 B
lead(compact)  = MAGIC(4) | profile(1) | nonce(4) | nblocks(2) | length(2) | CRC16(2) | 填充(1) = 16 B
body           = payload (1..65535 B)
```

**选择规则**（`lead_profile_for`）：仅当宽松引导头的 88 块占预算不到 2% 时才用它，
否则用紧凑档，把省下的 44 块全部让给载荷：

| 底图 | 块数 | 选中档位 | 引导占块 | 最大载荷 |
|---|---|---|---|---|
| 112×112 | 196 | compact | 44（22%） | 60 B |
| 128×128 | 256 | compact | 44（17%） | 90 B |
| 256×256 | 1024 | compact | 44（4%） | 441 B |
| 512×512 | 4096 | compact | 44（1%） | 1863 B |
| 1024×1024 | 16384 | standard | 88（0.5%） | 7548 B |
| 4096×4096 | 262144 | standard | 88（0.03%） | 105984 B |

要点：

- **码字长度必须是 8 字节的倍数**。每个 8×8 块存 4 bit，引导码字若不对齐这条车道，
  之后每个 body 块都会错位——这是不可恢复的。
- 引导头**永远只有一块**，接收方先只读它就能解出 `nblocks` 与 `length`，**不用猜**。
  这是把提取耗时从随载荷增长压到恒定的关键。
- nonce 与 `profile` 字节是**明文**（白化从其之后开始），接收方据此派生掩码并识别档位。
- 盲提取时接收方**依次试两档**，哪一档的引导头能通过 CRC 就用哪一档。

### 3.5 载体通道自动择优

极端颜色（纯红、纯黄）的 Y 通道会被 RGB 色域**裁剪卡死**（纯红的 luma 恒为 76，只能在 74–78 变动），
QIM 写入直接被裁掉。因此支持三个通道作为载体：

```python
CARRIER_ORDER = (0, 1, 2)          # Y, Cb, Cr
```

`_carrier_scores()` 对每个通道计算：

```
score = (RGB 往返稳定像素比例) × (0.35 + 0.65 × min(1, std/48))
```

稳定度优先（能裁剪的通道无论如何都不可用），动态范围次之。
`_pick_carrier()` 默认选 Y，只有其他通道明显更稳定（+0.02）才换。

`embed` 失败时还会依次尝试更粗的 `step ∈ {8,9,10,11,12,14}`，
用“写入后自己再提取一遍”验证成功才返回——**绝不静默产出坏数据**。

### 3.6 小图自动等比放大

尺寸不够时不是拒绝，而是按整数倍比例放大到“刚好够用”：

```python
scaled, original_size, resized = upscale_cover(image)
```

- 所需块数由**实际帧成本**反推（引导头 40 B + body 分块），不是固定常数。
- 用 `Image.LANCZOS`：保持画面清晰，且保留低频 DCT 结构（QIM 载体更稳）。
- 只放大到刚好够用，避免无谓的体积与失真。
- 下限：任一边 < 20 px 才拒绝（16×16 放大 7 倍 → 112×112 实测可用）。

## 4. 容量估算

### 4.1 公式

每个 8×8 块承载 **4 bit**（4 条车道）。一帧的比特成本：

```
bits = (lead_code_bytes + nblocks × (chunk + 16)) × 8
其中 lead_code_bytes = 22(compact) 或 44(standard)
     nblocks = ceil(payload / 207)，chunk = ceil(payload / nblocks)
```

引导头是**固定成本**，所以小图的容量被它压得最狠：
128×128 若用宽松档，32 字节握手就要 184 块（占 256 块的 72%）；
换紧凑档只需 140 块（55%），容量因此从 72 B 提到 90 B。

因此**容量与像素数成正比**：

```
可用比特 ≈ (width//8) × (height//8) × 4  =  像素数 / 16
可用字节 ≈ 像素数 × 0.0625  (毛容量)
实际载荷 ≈ 像素数 × 0.0072  (扣掉 RS 校验与帧头后)
```

即约 **0.058 bit/px** 的有效载荷密度（毛容量 0.0625 B/px 的 92%，
其余 8% 花在 RS 校验与引导头上）。小图比例会低一些（96² 只有 0.0037 B/px），
因为引导头是固定成本。

|---|---|---|---|---|---|
| 96² | 0.01 M | 34 B | 0.0037 | 11 | 1 |
| 128² | 0.02 M | 90 B | 0.0055 | 30 | 2 |
| 192² | 0.04 M | 234 B | 0.0063 | 78 | 7 |
| 256² | 0.07 M | 441 B | 0.0067 | 147 | 13 |
| 384² | 0.15 M | 1 035 B | 0.0070 | 345 | 32 |
| 512² | 0.26 M | 1 863 B | 0.0071 | 621 | 58 |
| 768² | 0.59 M | 4 242 B | 0.0072 | 1 414 | 132 |
| 1024² | 1.05 M | 7 548 B | 0.0072 | 2 516 | 235 |
| 1536² | 2.36 M | 17 015 B | 0.0072 | 5 671 | 531 |

> 而不是块不够用。

（“中文字”按 UTF-8 三字节/字折算；“X25519 公钥”= 32 B。）

### 4.3 与其他信道对比

| 信道 | 单位 | 密度 | 伪装对象 |
|---|---|---|---|
| 中文信道（本仓库） | 1 汉字 ≈ 11.55 bit | ~1.44 B/字 | 一段通顺中文 |
| 图片 DCT-QIM（本模块） | 1 块 = 4 bit | 0.0072 bit/px | 一张普通照片 |
| LSB（参考） | 1 像素 = 1~3 bit | 1~3 bit/px | 一张普通照片 |

图片信道远低于 LSB，但 LSB 重编码/压缩即毁，本方案能扛 JPEG q88 与轻微噪声、亮度、对比度扰动。

## 5. 底图要求

### 5.1 硬性要求

| 条件 | 要求 | 原因 |
|---|---|---|
| 最小边长 | ≥ 20 px（不足则自动等比放大） | 至少要有一个 8×8 块 |
| 容量 | 像素数 × 0.0072 ≥ 载荷字节 | 见 4.1 |
| 格式 | **PNG**（无损）为主通道 | JPEG 有损会破坏 QIM |

### 5.2 鲁棒性实测

| 处理 | 结果 |
|---|---|
| PNG 无损往返 | ✅ 全部通过（24/24 样例图） |
| JPEG q88 / q90 / q95 / q100 | ✅ 可提取 |
| JPEG q85 及以下 | ❌ 不保证（底图越大越抗） |
| 亮度 ±20、对比度 1.1× | ✅ 可提取 |
| 加噪 ±3 | ✅ 可提取 |
| 缩放 / 旋转 / 裁剪 | ❌ 必然破坏块网格，需重新握手 |

### 5.3 颜色限制

- 纯黑 / 白 / 灰 / 红 / 蓝 / 黄 / 品红：✅（自动切换 Cb/Cr 通道）
- 纯绿 (0,255,0)：Y=150 恰在色域边界，往返偏差 ±2 超过半格余量。
  会尝试更粗 step 与 Cb/Cr，仍失败则抛出**清晰中文错误**，不会静默写坏。
- 极低对比度、纯白噪声：✅

## 6. 与中文信道的整合

两者是**并列的信道后端**，共享“压缩 → 加密 → 帧封装”的前半段：

```
payload
  ├─ [中文信道]  压缩 → AES-GCM → 帧 → 算术编码 → 汉字 + 标点  → 文本
  └─ [图片信道]  payload → 帧(lead+body) → RS → DCT-QIM → PNG 图片
```

- **握手场景**（`handshake.py`）用图片信道：双方各发一张含 X25519 公钥的图，
  图片可经公开渠道传输而不像“密文”。
- **文本场景**（`codec.py` + `cli.py`）用中文信道。
- 二者可串联：图片信道的载荷本身可以是一段中文信道的伪装文本。

`chat_gui.py` / `run_chat.py` 演示图片信道的完整用法：双窗口互发图片完成
X25519 握手，之后用 AES-256-GCM 收发消息（主路径走 PNG 无损）。

## 7. GIF 动图

GIF 是**调色板格式**：每个像素是 256 色表里的一个索引。这带来两个麻烦：

- 把全彩图存成 GIF 会**重新量化**每个像素，误差常达几十级，远超一个 QIM 格点；
- 调色板颜色被大量相邻像素共享，改一个索引可能整片变色。

### 7.1 可行路径

关键观察：**GIF 帧本来就只有 ≤256 色，`quantize(256)` 对它们是精确无损的**。
所以流程改成：

```
解码首帧 → RGB
   ↓ 以「量化后」的像素为起点（保证配色可精确重现）
embed(step = 20 起，失败则 28→40→64→96→128)
   ↓ 重新量化 256 色
存成 GIF
   ↓ 从「重新加载的文件」再提取一遍验证
成功才返回，否则换更粗的 step 重试
```

`step` 从 20 起步（静图是 10）：调色板边界会吃掉一半格点余量，需要加倍格距。
`markovcryptor/gif_stego.py` 实现了全过程，并保证**返回前一定已经验证过能读回**。

### 7.2 只嵌首帧，体积几乎不变

GIF 的压缩基于**帧间差异**。若每帧都改，帧间相似性被破坏，文件会暴涨
（实测 +3.6% ~ +168%）。因此默认**只嵌第 0 帧**：其余帧与原文件逐字节一致。

实测 14 个样例（对比“不做隐写的同流程重编码”，以分离 PIL 自身的编码开销）：

| 0AEE69…gif | 17 | 938 K | 1078 K | 1082 K | **+0.3%** |
| 1c51ae…gif | 93 | 4342 K | 4367 K | 4379 K | **+0.3%** |

### 7.4 GIF 要求

| 条件 | 要求 |
|---|---|
| 首帧边长 | ≥ 20 px（不足则自动等比放大，所有帧同步放大以免抖动） |
| 帧数 | ≥ 1；**只有一帧的 GIF 也可用** |
| 体积增长 | 只嵌首帧时约 +0.1% ~ +5% |
| 透明色 | 自动压到黑底再嵌入，不影响提取 |
| 颜色数 | 少色（纯色/低色）也能用，会走更粗的 step |
| 不建议 | 已经被极高压缩率优化的 GIF（重编码会变大，但那是编码器差异） |

### 7.5 API

```python
from markovcryptor import gif_stego as G

data, report = G.embed_gif(gif_image, frame_bytes, key)          # 默认嵌首帧
data, report = G.embed_gif(gif_image, frame_bytes, key, frames_to_use=(0, 1))
payload, info = G.extract_gif(data, key)                          # 盲提取首帧
payload, info = G.extract_gif(data, key, frame_index=3)

G.capacity(gif_image)         # {"max_payload_bytes": ..., "frames": ...}
G.frames_of(gif_image)        # (frames, durations)
G.encode_gif(frames, durs)    # 拼回动图字节串
```

`report` 字段：`frames`、`embedded_frames`、`step`、`bytes`、`carriers`、
`max_block_change`、`payload_bytes`、`resized`。

## 8. 参数速查

```python
BLOCK = 8                      # DCT 块边长
LANES = 4                      # 每块车道数（= 4 bit/块）
MAGIC = b"MKX1"                # 帧标记
NONCE_BYTES = 8                # 帧内 nonce（明文）
NBLOCK_BYTES = 2               # RS 块数字段宽度

LEAD_COMPACT  = LeadProfile(index=2, nonce_bytes=4, nsym=6)    # 22 B 码字 = 44 块
LEAD_ROOMY_SHARE = 0.02        # 引导占比低于此才用宽松档

```

## 9. 主要 API

```python
from markovcryptor import image_stego as S

# 单次嵌入 / 提取
frame = S.build_frame(payload)                  # 构造帧
stego, report = S.embed(cover, frame, key)      # 写入，返回图 + 统计
payload = S.parse_frame(S.extract(stego, key)[0])   # 读回

# 不确定 step 时（embed 可能自动升 step）
payload, info = S.try_extract(image, key)

# 容量与可行性
S.max_payload_bytes(w, h)          # 最大载荷字节
S.check_cover(image, nbytes)       # (usable, reason)
S.plan(w, h, nbytes)               # 完整容量报告
S.suggest_size(image, nbytes)      # 需要的放大后尺寸
scaled, orig, resized = S.upscale_cover(image)
```
