## 1. 应该选哪条

| 你要做的事 | 用哪条 |
|---|---|
| 发一条短消息，不想让人看出在发消息 | 中文信道（输出像一段散文） |
| 藏一个文件，接受"发了一张图"这件事被看见 | 图片信道 |
| 载体本来就是表情包 / 动图 | GIF 信道 |
| 载荷大（> 100 KB） | 图片信道，大图（见 §3 容量表） |
| 消息必须能扛住聊天软件的二次压缩 | 都做不到，见 §5 |

一个关键区别：**中文信道不修改载体，它生成载体**。另外两条信道接收一张已有
的图片并把数据写进去。这个区别决定了 API 的形状（中文信道没有 `cover`）。

## 2. 中文文本信道

### 2.1 原理

载荷 → 压缩 → 加密（可选）→ 一阶马尔可夫链算术编码 → 汉字串。

解码是编码的逆过程：汉字串 → 退出每个汉字的算术区间，还原比特流 → 解密 → 解压。

**为什么一阶马尔可夫链**：零阶模型给每个汉字一个独立概率，输出会出现
"的了了了了"这种一眼假的串。一阶模型按"前一个汉字"给条件概率，输出的汉字搭配
在语料里出现过，读起来像正常中文。这是隐写的目标——**隐蔽性优先于压缩率**。

**为什么至少 64 个不同汉字**：词表小于 64 时，条件概率表太小，编码后的文本
重复度极高，且算术编码的区间划分过粗，容易在浮点精度上出错。训练时直接拒绝。

**标点**：数据只存在汉字里。标点是编码完成后按语料统计补的，
所以**去掉全部标点仍能解码**。这意味着标点不承载信息，可以被任意修改而不损坏消息。

### 2.2 容量

中文信道的容量不是"多少字节"，而是**多少汉字**：约每汉字 1.9~2.4 bit
（取决于模型的熵）。3000 字词表、典型新闻语料上：

```
载荷 100 B  ≈  400 汉字  ≈  一段话
载荷 1 KB   ≈  4000 汉字 ≈  一篇短文
```

比图片信道小两个数量级。这是有意的代价：换来"看起来像自然语言"。

### 2.3 要求

- **必须先训练模型**。没有模型时信道不可用，错误信息是
  `中文信道需要先训练模型`，附带 `markovcryptor train --corpus <语料>` 的提示。
- **解码方必须有同一个模型文件**。模型不同则概率表不同，解出来是乱码或
  `NoHiddenFrame`。这不是 bug，是协议的一部分——模型本身就是密钥的一部分。
- **加密可选**。给了 `password` 走 AES-GCM，不给就只做编码。**不加密时消息不保密**，
  只是"看起来像中文"；任何人有同一个模型都能解出载荷。

### 2.4 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `password` | `null` | 口令。给了就用 AES-GCM 加密载荷；留空则只做编码不做加密 |
| `add_punctuation` | `true` | 按语料统计补标点，让输出更像自然中文 |

## 3. 图片信道（摘要）

完整原理见 [IMAGE_STEGO.md](IMAGE_STEGO.md)。

一句话：把数据写进 8×8 块 DCT 的**中频系数**，用**中心格点 QIM** 量化，
块顺序由密钥派生，因此**盲提取**（不需要原图）。

### 3.1 容量实测（B/px ≈ 0.0072）

| 边长 | 容量 | 边长 | 容量 |
|---|---|---|---|
| 96² | 34 B | 768² | 4 242 B |
| 128² | 90 B | 1024² | 7 548 B |
| 192² | 234 B | 1536² | 17 015 B |
| 256² | 441 B | 2048² | 30 282 B |
| 384² | 1 035 B | 4096² | 105 984 B |
| 512² | 1 863 B | | |

引导头是固定成本（按块计价），小图的固定开销占比很高——这是 128² 只有 90 B
而 256² 有 441 B 的原因。

### 3.2 要求

- 最小 40 px，小于 120 px 时按需等比放大（`upscale=true`，默认开）。
- **输出必须是 PNG**。JPEG 会破坏 QIM 格点，提取必然失败。
- 底图不能是纯饱和色（`底图颜色极端…请换一张图`）。
- 通道优先 Y，非 Y 需超出 0.02 才胜出。

### 3.3 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `step` | `10.0` | QIM 步长。越大越耐压缩/缩放，改动越明显 |
| `upscale` | `true` | 小图自动等比放大到刚好装下载荷 |
| `include_jpeg` | `false` | 额外产出一份 JPEG（**通常无法提取**） |
| `jpeg_quality` | `95` | 额外 JPEG 的质量 |

## 4. GIF 动图信道（摘要）

### 4.1 与图片信道的关键差异

GIF 每帧只有 256 色。图片信道的 QIM 写完之后要重新量化到 256 色，
量化误差可能超过半格而翻转判决。所以 GIF 信道**从粗步长起试**：

```
step = 20 → 28 → 40 → 64 → 96 → 128
每个 step：写入 → 存成 GIF → 重新加载 → 尝试提取
第一个能稳定往返成功的 step 就是答案
```

### 4.2 只嵌首帧

默认只改第一帧，其余帧像素不动。原因：动图帧间压缩（帧差）会让改动传播，
而逐帧嵌入会让体积成倍增长。

### 4.3 要求与限制

- 必须是**多帧**动图。单帧会报
  `这是单帧图片，请改用图片通道；GIF 通道专为多帧动图设计`。
- 小图可等比放大，但最多 2× 且结果不超过 160 KB——放大作用于每一帧，
  体积按平方增长。
- 大面积纯色/渐变的动图无法稳定承载（错误信息会列出试过的所有 step 和真实原因）。

### 4.4 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `step` | `null` | 留空则自动从 20 试到 128；给了就用给定值，失败则报错 |
| `frame_index` | `0` | 藏进第几帧 |
| `upscale` | `true` | 小动图自动放大 |

## 5. 三信道对比

| | 中文文本 | 图片 | GIF |
|---|---|---|---|
| 载体 | **生成** | 修改 | 修改 |
| 盲提取 | 需要模型 | ✅ | ✅ |
| 容量 | ~1 KB | 按像素²，最大 ~100 KB | 同图片（仅首帧） |
| 输出格式 | `.txt` | `.png`（必须） | `.gif` |
| 抗二次压缩 | ❌ | ❌ | ❌ |
| 加密 | 可选（AES-GCM） | 内置（AES-GCM） | 内置（AES-GCM） |
| 速率 | 慢（纯 Python 算术编码） | 快 | 中 |
| 并发建议 | 4 | 4 | 2 |

**没有一条信道能扛住有损二次压缩。** 微信/QQ 发送图片时会重新编码 JPEG，
那条路径上的 QIM 格点会被破坏。要传输必须用**文件**方式（不走图片预览）。
这是所有 DCT 域隐写的共同限制，不是本项目的缺陷。

## 6. 错误分类

每个错误都带稳定的 `code`、原始原因 `reasons` 和可操作建议 `hints`。

| code | HTTP | 含义 | 典型原因 |
|---|---|---|---|
| `invalid_input` | 422 | 调用方传错了 | 参数越界、文件为空、options 不是 JSON 对象 |
| `unsupported_carrier` | 415 | 载体格式不支持 | 给了 GIF 但选了图片信道 |
| `capacity_exceeded` | 413 | 装不下 | 载荷太大、图太小、GIF 放大代价过高 |
| `bad_key` | 401 | 密钥错 | 口令错、模型文件不匹配 |
| `no_hidden_frame` | 404 | 没有隐写帧 | 普通图片、或用了另一条信道提取 |
| `carrier_damaged` | 422 | 载体被破坏 | 图像被裁剪、重新压缩过 |
| `channel_unavailable` | 503 | 信道不可用 | 中文信道没有模型 |

**`reasons` 永远保留原文，不会笼统化。** 例如容量不足时给出的是
`GIF 太小：155×60 只能容纳 28 字节，需要 32 字节。放大 1.4× 会让全部 3 帧的
像素量变成 2.0 倍（原文件 12 KB）…`，而不是"无法稳定承载"。
